StreamVault is a change data capture pipeline that lands Postgres changes into Apache Hudi tables and serves the tables to Trino for SQL analytics. It follows the shape of a production streaming platform in miniature. Rows change in Postgres. Debezium reads the write ahead log. Kafka carries the change events. A Spark Structured Streaming job applies the events to Hudi tables on object storage. Trino reads the finished tables through the Hudi connector.

The two source tables are orders and inventory for a small retail dataset. The data is synthetic and generated by a script in this repo. Nothing in here points at a real system.

## What is inside

**cdc** holds the Debezium connector definitions for the orders and inventory tables plus a small shell script that registers both connectors with Kafka Connect.

**ingestion** holds the Spark streaming jobs and the plain Python transform code the jobs call. The transforms sit apart from Spark on purpose so they can be unit tested without a cluster.

**lakehouse** holds the table definitions for the two Hudi tables and notes on the partitioning and merge choices.

**sql** holds the Trino queries I run against the finished tables. Daily revenue, current stock levels, orders that sat untouched for too long, and the end of day snapshot that freezes each day stock positions before the next day of changes lands.

**sample-data** holds the Postgres schema and the generator that fills it with orders and inventory rows.

**tests** holds the pytest suite for the transform code.

## Run it locally

You need Docker with the compose plugin and Python 3.11 or newer for the tests. Everything else runs in containers.

1. Start the stack with `docker compose up -d`. This brings up Postgres, Kafka, Kafka Connect, MinIO, and Trino.
2. Load the schema and seed data with `python sample-data/generate_data.py --rows 500`. The script writes a SQL file and applies it to the local Postgres container.
3. Register the connectors with `sh cdc/register-connectors.sh`. Debezium starts streaming changes into the topics `streamvault.public.orders` and `streamvault.public.inventory`.
4. Start the ingestion job with the submit command in `ingestion/README.md`. Change a few rows in Postgres and watch them land in the Hudi tables.
5. Open the Trino CLI against `localhost:8080` and run the queries in the sql folder.

## Design choices worth knowing

The orders table uses merge on read because order rows update often and readers mostly scan recent days. The inventory table uses copy on write because stock reads are frequent and the table is small. Both tables key on the source primary key and use the source update timestamp as the precombine field, so a late arriving older change never overwrites a newer row. Partitioning is by event date on orders and by warehouse on inventory.

Delete events are kept as tombstone rows with a deleted flag instead of being dropped. Downstream queries filter them out. Keeping them makes the pipeline auditable and lets a bad upstream delete be undone without a rebuild.

## Tests

Run `python -m pytest` from the repo root. The suite covers the Debezium envelope parsing, the row transforms, and the dedupe logic that picks the winning version of a row.
